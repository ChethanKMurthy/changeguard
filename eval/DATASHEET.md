# Datasheet: ChangeGuard evaluation dataset

Following the structure of *Datasheets for Datasets* (Gebru et al.). Numbers are
for the dataset at SHA-256 `b65381532aba57ce…` (see `reports/latest.json`,
`manifest.dataset_sha256`).

## Motivation

**Why was it created?** To measure whether ChangeGuard points reviewers at the
lines that matter in a code change, how often it raises false alarms on safe
changes, and whether every finding's evidence is real. No public dataset labels
*review-worthy locations in a diff* with the inputs this tool needs (patch,
base snapshot, optional coverage report), so one was written.

**Who created it?** The same author who wrote the ChangeGuard rules. This is the
dataset's most important limitation and is discussed below.

## Composition

| | |
|---|---|
| Cases | 67 code changes: 33 dev, 21 holdout, 13 holdout-v2 |
| Languages | Python 43, TypeScript 14, JavaScript 6, SQL 3, JSON 1 |
| Labels | 65 expected labels, plus 38 acceptable-observation entries |
| Negative controls | 9 cases with no labels (safe changes) |
| Difficulty (author's estimate) | 28 easy, 35 medium, 4 hard |
| Modes | 66 with a base snapshot, 1 diff-only |
| Coverage reports | 1 case includes a Cobertura report |

Label categories: security 16, breaking change 15, test integrity 5, logic
change 5, dependency 5, error handling 4, data migration 4, concurrency 3,
secret exposure 2, behaviour change 2, correctness 2, prompt injection 1,
coverage gap 1.

Each case directory holds `case.yaml` (metadata and labels), `base/` and
`head/` (small synthetic repositories), `change.patch` (generated by git from
the two trees), and optionally a coverage report. Cases contain no personal
data. Secret-like strings in the secret-exposure cases are random strings made
up for those cases; none is a real credential.

## Collection process

Every case is **synthetic, authored for this dataset**: a small repository and a
change written to exercise one risk pattern (sometimes two), plus negative
controls written to resemble risky changes that are actually safe. Patches are
produced by `git diff` (`backend/tools/make_patch.py`), never written by hand.

The splits were written in order. The dev split came first and the rules were
developed against it. Each holdout split was written after the ruleset was
frozen, labelled before any system ran on it, and evaluated once. Its first-run
output is kept verbatim in `reports/runs/`.

## Labelling

Labels follow [`LABELING.md`](LABELING.md): a label marks where a careful reviewer
should stop, with a category describing the consequence. There is a single
labeller and no inter-annotator agreement has been measured. One label
correction was made after a first run; it is recorded in
`reports/holdout-history.json` together with the reason.

## Uses

**Intended:** regression testing of ChangeGuard (the CI gate replays it on
every change), comparing rule changes, comparing language models under the same
prompt, and illustrating the evaluation method.

**Not suitable for:** claims about effectiveness on real-world repositories,
comparisons with other tools on equal terms (the cases were written with this
tool's input format and rule coverage in mind), or estimating incident rates.

## Known limitations and biases

- **Same author for rules and cases.** Dev-split results are optimistic by
  construction. Holdout splits reduce but do not remove this: they share the
  author's style and blind spots.
- **Small.** With 65 labels, one case moves recall by about 1.5 points. Bootstrap
  intervals are reported for that reason and are wide.
- **Synthetic and tidy.** Real changes are larger, noisier, and mix several
  concerns; the cases here mostly isolate one.
- **Language skew.** Python dominates; Go, Java, and Rust are absent.
- **Single labeller**, so label noise is unmeasured.

## Maintenance

New cases are added under the procedure in `LABELING.md` section 6. Any change
to existing labels is recorded as described in section 4. The dataset hash in
each evaluation report identifies exactly which version produced it.
